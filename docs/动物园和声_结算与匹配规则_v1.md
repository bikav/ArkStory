# 《动物园和声》结算与匹配规则 v1

## 1. 文档目的

本文件用于定义《动物园和声》MVP 阶段的匹配规则、对局结束规则与结算规则。

平台口径说明：

- 正文默认按 `TapTap Android 首发` 编写
- 规则层本身为平台无关设计
- 微信小游戏相关差异说明统一放在文末“微信小游戏适配参考”章节

设计目标：

1. 明确排位赛、休闲赛、好友房的匹配与开局规则
2. 明确超时、投降、掉线、异常中断等对局结果判定
3. 明确分数结算、金币奖励、星级变化的统一规则
4. 为服务端实现、前端展示与测试验收提供统一标准

## 2. 规则范围

本文件覆盖以下内容：

1. 匹配模式与进入条件
2. 匹配分组与房间创建
3. 开局与发牌规则
4. 对局终局触发条件
5. 正常结算规则
6. 异常结算规则
7. 排位升星与保护规则
8. 奖励结算与发放要求

本文件不覆盖以下内容：

1. 具体接口定义
2. WebSocket 事件包结构
3. 卡牌构筑细则
4. UI 表现细节

## 3. 对局模式定义

MVP 建议开放三种模式：

### 3.1 排位赛

特点：

1. 使用玩家当前选择的合法出战牌库
2. 参与段位星级变化
3. 胜负结果影响赛季战绩
4. 结算金币与段位奖励

### 3.2 休闲赛

特点：

1. 使用合法出战牌库
2. 不影响段位星级
3. 保留基础金币奖励
4. 可用于测试新构筑

### 3.3 好友房

特点：

1. 由玩家主动创建房间
2. 可邀请指定玩家加入
3. 默认不影响段位星级
4. 金币奖励可减半或关闭

MVP 建议：

- 排位赛：全量开放
- 休闲赛：全量开放
- 好友房：若排期紧，可放到 P1

## 4. 匹配前置条件

玩家进入排位赛或休闲赛前，服务端必须校验：

1. 玩家登录态有效
2. 玩家当前不在其他匹配队列中
3. 玩家当前不在其他房间或对局中
4. 出战牌库存在
5. 出战牌库属于当前玩家
6. 出战牌库满足构筑规则

构筑合法性规则如下：

1. 牌库固定 `12 张`
2. 同名牌最多 `1 张`
3. 总成本上限为 `24`
4. 白色卡牌至少 `3 张`
5. 红色卡牌最多 `2 张`

若任一条件不满足，应拒绝进入匹配流程。

## 5. 匹配分组规则

## 5.1 排位匹配

排位赛建议按以下维度匹配：

1. 当前大段位
2. 当前星数
3. 最近对局隐藏分
4. 等待时长

MVP 建议优先使用：

1. 大段位
2. 星数
3. 等待时长扩圈

匹配扩圈建议：

1. 前 10 秒：只匹配同段位、相近星数玩家
2. 10 到 20 秒：允许扩大到相邻星差
3. 20 秒后：允许扩大到邻近段位

注意：

- 不建议为了极短等待时间牺牲过多公平性
- 段位极高玩家可使用更宽松扩圈

## 5.2 休闲匹配

休闲赛可弱化段位限制，优先追求开局速度。

建议维度：

1. 当前是否在线可匹配
2. 等待时长
3. 最近对局胜率范围

## 5.3 好友房匹配

好友房不走自动匹配，采用：

1. 创建房间
2. 生成房间号或邀请链接
3. 好友加入
4. 双方确认后开局

## 6. 开局规则

匹配成功后，服务端执行以下初始化流程：

1. 锁定双方出战牌库
2. 创建 `match_room`
3. 记录双方 `match_player`
4. 生成本局随机种子
5. 初始化中央地形袋与地形市场
6. 对双方牌库分别独立洗牌
7. 双方各自抽取 4 张动物牌进入备选区
8. 随机决定先手玩家
9. 进入正式对局

### 6.1 牌库洗牌与备选牌

规则要求：

1. 每位玩家带入固定 12 张合法牌库
2. 12 张牌必须完全随机洗牌
3. 初始 4 张备选牌从洗匀后的牌库顶依次抽取
4. 不允许按颜色稀有度调整发牌权重

这意味着：

- 白、蓝、金、红牌在发牌阶段没有额外权重修正
- 初始备选区完全由随机洗牌结果决定

### 6.2 先手决定

MVP 建议：

1. 通过服务端随机决定先手
2. 先手与后手概率均为 50%

后续若需要提高公平性，可引入：

1. 同局双回合镜像赛制
2. 长期先手率平衡

但 MVP 不必实现。

## 7. 对局内通用结算原则

对局过程中所有关键状态由服务端权威管理：

1. 地形放置是否合法
2. 动物方块是否满足图案要求
3. 动物牌完成进度
4. 地形分与动物牌分
5. 终局是否触发

客户端可以做预览，但最终结果必须以服务端复算为准。

## 8. 正常终局条件

满足以下任一条件时，触发正常终局检测：

### 8.1 地形袋无法补满中央市场

当回合结束后，若服务端无法将中央市场补足到规则要求的完整状态，则进入终局流程。

### 8.2 任一玩家版图仅剩 2 个及以下可用空位

当回合结束后，若任一玩家版图仅剩 `2 个及以下空位`，则进入终局流程。

### 8.3 终局后的补齐回合

为了保证双方行动次数一致，终局触发后应补齐回合数。

MVP 建议规则：

1. 若终局由当前玩家回合结束时触发
2. 则另一名玩家获得最后 1 个完整回合
3. 双方完成同样数量的回合后进入最终结算

服务端必须记录：

1. `end_trigger_type`
2. `end_trigger_turn_no`
3. `final_round_player_id`

## 9. 正常分数结算规则

最终分数由两部分构成：

1. 地形分
2. 动物牌分

总分公式：

`final_score = terrain_score + animal_card_score`

### 9.1 地形分

按《动物园和声》当前沿用的地形计分规则计算：

1. 树木地形得分
2. 山地得分
3. 田野得分
4. 建筑得分
5. 水域得分

所有地形得分由服务端在终局时统一复算。

### 9.2 动物牌分

每张动物牌按其当前完成档位计分。

计分原则：

1. 已进入进行中区域但未放任何动物方块的牌，按 `0 分`
2. 放置 1 个、2 个、3 个动物方块时，按该牌对应档位分值计分
3. 已完成牌仍参与最终总分计算

### 9.3 平局规则

若双方总分相同，则判定为平局。

MVP 建议：

1. 不做复杂二级比较
2. 直接按平局处理

后续若需要更强竞技性，可增加加赛或次级比较字段，但首版不建议加入。

## 10. 胜负判定规则

### 10.1 正常终局

1. 总分更高的一方获胜
2. 总分相同则平局

### 10.2 投降终局

若玩家主动投降：

1. 投降方直接判负
2. 对手直接判胜
3. 不再继续对局剩余流程
4. 若已有中间分数，可记录但不作为胜负依据

### 10.3 超时终局

若玩家在规定时限内未完成回合：

1. 超时方直接判负
2. 对手直接判胜

MVP 建议：

- 不做复杂托管
- 先做“超时直接负”

### 10.4 异常断线终局

若玩家掉线后在容忍时间内未重连成功：

1. 掉线方直接判负
2. 对手直接判胜

MVP 建议：

1. 断线宽限时间：`60 秒`
2. 宽限期间允许重连恢复
3. 超过宽限期仍未恢复则结束对局

### 10.5 系统异常终局

若发生服务端异常、严重校验失败或风控问题：

1. 可将本局标记为异常对局
2. 暂不发放排位结果
3. 进入人工复核或自动回滚流程

## 11. 回合超时规则

MVP 建议为每回合设置倒计时。

建议值：

1. 常规回合时间：`90 秒`
2. 网络抖动缓冲：`5 秒`

回合超时判定：

1. 客户端倒计时仅用于展示
2. 服务端时间为唯一权威
3. 倒计时结束且玩家未合法结束回合，则判为超时

超时处理：

1. 首版直接判负
2. 不执行自动摆放或托管

## 12. 掉线与重连规则

### 12.1 掉线判定

满足以下任一情况时，可视为连接中断：

1. 心跳超时
2. WebSocket 主动断开
3. 客户端进程被挂起过久

### 12.2 重连恢复

掉线后，玩家可在宽限期内通过房间 token 重新加入对局。

恢复要求：

1. 重新建立 WebSocket 连接
2. 使用 `match.join` 且 `resume = true`
3. 服务端下发当前最新状态快照

### 12.3 掉线结算

若玩家在宽限期内恢复：

1. 对局继续
2. 不额外处罚

若玩家未在宽限期内恢复：

1. 判定掉线方负
2. 对手胜

## 13. 投降规则

MVP 建议支持玩家主动投降。

投降限制：

1. 对局开始后才可投降
2. 结算阶段不可投降

投降处理：

1. 投降方战绩记负
2. 对手战绩记胜
3. 正常发放胜负奖励
4. 排位模式正常执行升降星

## 14. 排位星级规则

当前段位体系：

1. 实习饲养员
2. 正式饲养员
3. 展馆管理员
4. 园区主管
5. 副园长
6. 园长
7. 五星园长
8. 世界保育馆长

### 14.1 基础升降规则

MVP 建议：

1. 胜利：`+1 星`
2. 平局：`0 星`
3. 失败：`-1 星`

### 14.2 新手保护

MVP 建议：

1. `实习饲养员` 段位失败不掉星
2. 其余段位失败正常掉星

### 14.3 升段规则

1. 当前段位星数满后进入下一段位
2. 升段时星数按新段位初始值重置

### 14.4 掉段规则

MVP 建议：

1. 非保护段位在星数为 0 时再次失败，可掉到上一段位
2. 是否掉段保底可在赛季后续再加，首版不强求

### 14.5 最高段位规则

`世界保育馆长` 建议使用积分榜或排名机制。

MVP 可先做简化版本：

1. 到达最高段位后不再按普通星级推进
2. 记录额外胜场或积分

## 15. 金币奖励规则

双方均可根据最终结果获得金币奖励，避免“输一局白打”。

推荐公式：

`gold_reward = 40 + final_score * 2 + result_bonus`

其中：

1. 胜利奖励：`result_bonus = 30`
2. 平局奖励：`result_bonus = 15`
3. 失败奖励：`result_bonus = 0`

### 15.1 示例

1. `92 分战败`：`40 + 92*2 = 224`
2. `98 分获胜`：`40 + 98*2 + 30 = 266`
3. `85 分平局`：`40 + 85*2 + 15 = 225`

### 15.2 异常对局奖励

对于投降、超时、掉线：

MVP 建议：

1. 胜方按正常奖励发放
2. 负方若为投降、超时、掉线，可仅发放基础参与奖励或降额奖励

建议方案：

1. 投降负方：`20 金币`
2. 超时负方：`10 金币`
3. 掉线负方：`10 金币`

这样既保留最低参与反馈，又不鼓励消极退出。

## 16. 结算结果字段建议

服务端结算结果建议至少包含：

1. `match_id`
2. `match_type`
3. `end_reason`
4. `winner_player_id`
5. `player_a_final_score`
6. `player_b_final_score`
7. `player_a_terrain_score`
8. `player_b_terrain_score`
9. `player_a_animal_score`
10. `player_b_animal_score`
11. `player_a_gold_reward`
12. `player_b_gold_reward`
13. `player_a_star_change`
14. `player_b_star_change`
15. `rank_before`
16. `rank_after`

## 17. 结算流程

服务端推荐结算顺序：

1. 锁定对局状态为 `ending`
2. 复算双方最终版图
3. 复算地形分
4. 复算动物牌分
5. 得出最终总分与胜负关系
6. 计算金币奖励
7. 计算排位星级变化
8. 写入 `match_result`
9. 写入 `reward_log`
10. 写入段位更新记录
11. 广播 `match.end`
12. 对外提供结果查询接口

## 18. 反作弊与复算要求

结算阶段必须满足：

1. 所有分数由服务端根据动作日志复算
2. 客户端上传的本地分数仅作展示参考
3. 若服务端复算与过程状态不一致，应以服务端复算为准
4. 若发现严重分数不一致，应触发 `6007`

应重点记录：

1. 随机种子
2. 初始双方牌库顺序
3. 地形袋顺序或抽取序列
4. 每步动作日志
5. 状态版本变化

## 19. 典型场景规则

### 19.1 玩家正常打完并获胜

结果：

1. 判定胜利
2. 发放正常金币
3. 排位模式 `+1 星`

### 19.2 玩家正常打完但平局

结果：

1. 判定平局
2. 双方发放平局金币
3. 排位模式星数不变

### 19.3 玩家中途投降

结果：

1. 投降方判负
2. 对手判胜
3. 直接结束对局

### 19.4 玩家掉线 20 秒后恢复

结果：

1. 允许继续对局
2. 不作失败处理

### 19.5 玩家掉线超过 60 秒

结果：

1. 掉线方判负
2. 对手判胜

### 19.6 玩家超时未操作

结果：

1. 超时方判负
2. 对手判胜

## 20. 与错误码联动建议

本文件中的关键异常建议与以下错误码联动：

1. 非法牌库匹配：`4004`
2. 已在队列中重复匹配：`4001`
3. 已在其他房间中：`4005`
4. 心跳超时：`5018`
5. 结算未就绪：`6001`
6. 奖励发放失败：`6002`
7. 分数校验不一致：`6007`

## 21. MVP 推荐落地方案

若首版需要控制复杂度，建议采用如下方案：

1. 匹配模式只做排位赛和休闲赛
2. 回合超时直接判负，不做托管
3. 支持断线重连，宽限时间 60 秒
4. 支持主动投降
5. 平局直接按平局处理，不做额外比较
6. 胜负金币按统一公式发放
7. 排位先做简单 `胜+1 / 平0 / 负-1`

这套方案实现成本相对可控，同时足以支撑 MVP 竞技闭环。

## 23. 微信小游戏适配参考

以下内容仅作为后续适配微信小游戏时的参考，不影响 TapTap Android 首发规则主流程：

1. 匹配、终局、结算和奖励公式本身无需改动。
2. 若微信小游戏更强调碎片化在线时长，可在后续版本缩短回合时间或增加轻量休闲模式。
3. 若微信小游戏平台对长连接稳定性提出额外限制，应重点保留“掉线重连 + 快照恢复”机制。
