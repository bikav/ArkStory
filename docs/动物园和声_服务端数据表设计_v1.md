# 《动物园和声》服务端数据表设计 v1

## 1. 文档目的

本文件用于定义《动物园和声》MVP 阶段的服务端核心数据表结构。

平台口径说明：

- 正文默认按 `TapTap Android 首发` 编写
- 能做成平台无关字段的，优先不写死渠道专属命名

目标：

1. 支撑 TapTap Android 首发账号体系
2. 支撑卡牌收集、构筑、对局、结算、排位
3. 满足服务端校验与反作弊的最小需求
4. 为后续数据库设计、接口设计和联调提供统一底稿

## 2. 设计范围

本版本覆盖以下数据域：

1. 玩家账号
2. 玩家资源
3. 玩家持卡
4. 玩家牌库
5. 卡牌静态配置引用
6. 对局房间与回放
7. 赛季与段位
8. 抽卡与奖励日志

本版本不展开：

1. 公会
2. 社交消息
3. 活动复杂任务系统
4. 商城订单明细

## 3. 设计原则

### 3.1 静态配置与玩家数据分离

- 卡牌定义、成本、图案、标签属于静态配置
- 玩家拥有数量、牌库编组、使用记录属于动态数据

### 3.2 结算结果必须可复算

服务端至少需要保留：

1. 对局初始随机种子
2. 关键行动日志
3. 结算快照

这样才能在争议或异常时复盘。

### 3.3 MVP 优先最小闭环

先保证：

- 能登录
- 能抽卡
- 能组牌
- 能对战
- 能结算
- 能升段

复杂统计和运营系统可后补。

## 4. 数据实体总览

建议 MVP 最少包含以下表：

1. `player_account`
2. `player_resource`
3. `player_card_inventory`
4. `player_deck`
5. `player_deck_card`
6. `season_info`
7. `player_rank`
8. `match_room`
9. `match_player`
10. `match_action_log`
11. `match_result`
12. `gacha_log`
13. `reward_log`

如果数据库层希望再进一步拆分，也可以增加：

14. `player_profile`
15. `client_version_log`
16. `anti_cheat_event`

## 5. 静态配置引用说明

卡牌静态配置不建议存在业务数据库表里手工维护，而建议直接引用配置文件：

- `动物园和声_卡牌配置表_json草案_v1.json`

服务端运行时加载该配置，并使用 `card_id` 作为全局唯一引用键。

因此动态表里只保存：

- `card_id`
- 数量
- 状态
- 牌库引用关系

不重复存储分值、图案、标签等静态信息。

## 6. 玩家账号域

## 6.1 player_account

用途：玩家主账号表

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| player_id | bigint | 玩家主键 |
| primary_platform | varchar(32) | 首登平台，默认 taptap_android |
| platform_user_id | varchar(128) | 平台用户唯一标识 |
| platform_union_id | varchar(128) | 跨应用统一标识，可空 |
| nickname | varchar(64) | 玩家昵称 |
| avatar_url | varchar(255) | 头像地址 |
| register_time | datetime | 注册时间 |
| last_login_time | datetime | 最近登录时间 |
| login_status | tinyint | 账号状态，1 正常，0 封禁 |
| tutorial_step | int | 当前新手引导进度 |
| created_at | datetime | 创建时间 |
| updated_at | datetime | 更新时间 |

索引建议：

- 主键：`player_id`
- 唯一索引：`primary_platform + platform_user_id`
- 普通索引：`last_login_time`

## 6.2 player_profile

用途：玩家扩展信息表，可选

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| player_id | bigint | 玩家 ID |
| display_name | varchar(64) | 展示昵称 |
| signature | varchar(255) | 个性签名 |
| selected_deck_id | bigint | 当前出战牌库 |
| highest_rank_tier | int | 历史最高段位 |
| total_match_count | int | 总对局数 |
| total_win_count | int | 总胜场 |
| created_at | datetime | 创建时间 |
| updated_at | datetime | 更新时间 |

## 7. 玩家资源域

## 7.1 player_resource

用途：玩家资源总表

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| player_id | bigint | 玩家 ID |
| gold_coin | int | 金币 |
| gem | int | 付费货币，可先保留 |
| card_shard | int | 碎片或保育券 |
| rank_star_protect | int | 段位保护次数，可空 |
| created_at | datetime | 创建时间 |
| updated_at | datetime | 更新时间 |

说明：

- MVP 实际只启用 `gold_coin`
- `gem` 和 `card_shard` 可先保留字段，为后续抽卡和重复转化做准备

## 7.2 reward_log

用途：资源变化流水表

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| log_id | bigint | 主键 |
| player_id | bigint | 玩家 ID |
| reward_type | varchar(32) | 资源类型，如 gold_coin |
| change_amount | int | 变动值，正负皆可 |
| before_amount | int | 变动前 |
| after_amount | int | 变动后 |
| source_type | varchar(32) | 来源，如 match_reward、gacha_cost |
| source_id | varchar(64) | 来源 ID，可空 |
| remark | varchar(255) | 备注 |
| created_at | datetime | 创建时间 |

作用：

- 审计资源变动
- 排查重复发奖和扣费异常

## 8.1 player_card_inventory

用途：玩家拥有卡牌表

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| player_id | bigint | 玩家 ID |
| card_id | varchar(16) | 卡牌 ID |
| owned_count | int | 持有数量 |
| obtained_first_time | datetime | 首次获得时间 |
| last_obtained_time | datetime | 最近获得时间 |
| created_at | datetime | 创建时间 |
| updated_at | datetime | 更新时间 |

主键建议：

- 联合主键：`player_id + card_id`

说明：

- 如果后续做卡牌升级或皮肤，再增补字段
- MVP 阶段只需要知道玩家是否拥有，以及重复数量

## 8.2 gacha_log

用途：抽卡流水表

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| log_id | bigint | 主键 |
| player_id | bigint | 玩家 ID |
| gacha_type | varchar(32) | 卡包类型 |
| consume_type | varchar(32) | 消耗类型 |
| consume_amount | int | 消耗数量 |
| result_json | json | 抽卡结果 |
| random_seed | varchar(64) | 抽卡随机种子 |
| created_at | datetime | 创建时间 |

说明：

- `result_json` 建议直接记录本次获得的 `card_id` 列表

## 9. 牌库构筑域

## 9.1 player_deck

用途：玩家牌库主表

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| deck_id | bigint | 牌库主键 |
| player_id | bigint | 玩家 ID |
| deck_name | varchar(64) | 牌库名称 |
| is_active | tinyint | 是否当前出战牌库 |
| total_cost | int | 当前总成本 |
| white_count | int | 白色卡数量 |
| blue_count | int | 蓝色卡数量 |
| gold_count | int | 金色卡数量 |
| red_count | int | 红色卡数量 |
| deck_status | tinyint | 1 合法，0 非法 |
| created_at | datetime | 创建时间 |
| updated_at | datetime | 更新时间 |

说明：

- 这些统计字段可以冗余存储，方便快速校验和展示
- 真实合法性仍应以服务端实时校验为准

## 9.2 player_deck_card

用途：牌库卡牌明细表

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| deck_id | bigint | 牌库 ID |
| player_id | bigint | 玩家 ID |
| card_id | varchar(16) | 卡牌 ID |
| slot_index | int | 在牌库中的显示顺序 |
| created_at | datetime | 创建时间 |

主键建议：

- 联合主键：`deck_id + card_id`

业务校验：

1. 同一牌库必须恰好 12 张
2. 同名牌只能出现 1 次
3. 总成本不能超过 24
4. 白色至少 3 张
5. 红色最多 2 张

## 11. 对局域

## 11.1 match_room

用途：对局主表

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| match_id | bigint | 对局 ID |
| match_type | varchar(32) | 排位 / 休闲 / 好友 |
| season_id | bigint | 所属赛季，可空 |

| first_player_id | bigint | 先手玩家 |

## 11.2 match_player

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| match_id | bigint | 对局 ID |
| player_id | bigint | 玩家 ID |
| deck_id | bigint | 使用的牌库 ID |
| deck_snapshot_json | json | 本局实际带入 12 张牌快照 |

| result_type | varchar(16) | win / lose / draw |

| rank_star_change | int | 星级变动 |
| created_at | datetime | 创建时间 |

说明：

- `deck_snapshot_json` 很关键，避免玩家赛后改牌库导致记录失真
- `opening_option_json` 用于确认开局 4 张备选牌是如何发出的

| settle_version | varchar(16) | 结算规则版本 |
| is_verified | tinyint | 是否已服务端校验 |

## 13. 表关系说明

核心关系如下：

1. `player_account` 1 对 1 `player_resource`
2. `player_account` 1 对多 `player_card_inventory`
3. `player_account` 1 对多 `player_deck`
4. `player_deck` 1 对多 `player_deck_card`
5. `season_info` 1 对多 `player_rank`
6. `match_room` 1 对 2 `match_player`
7. `match_room` 1 对多 `match_action_log`
8. `match_room` 1 对 1 `match_result`

## 14. 关键业务校验点

服务端至少应执行以下校验：

### 14.1 构筑校验

1. 牌库必须为 12 张
2. 同名牌最多 1 张
3. 总成本不超过 24
4. 白色至少 3 张
5. 红色最多 2 张
6. 玩家必须真实拥有这些卡牌

### 14.2 对局发牌校验

1. 对局开始时 12 张牌必须完整洗牌
2. 开局 4 张备选牌必须从洗牌结果顶部依次抽出
3. 不允许对白蓝金红做额外概率修正

### 14.3 对局动作校验

1. 选择地形组必须存在
2. 地形放置必须合法
3. 动物牌选择必须来自当前 4 张备选牌
4. 进行中动物牌不能超过 4 张
5. 动物方块放置必须满足图案要求

### 14.4 结算校验

1. 地形分服务端复算
2. 动物牌分服务端复算
3. 胜负结果服务端确认
4. 金币奖励与排位变化服务端落库

## 15. 推荐接口依赖关系

为了让前后端协作清晰，建议后续接口围绕以下表设计：

1. 登录：`player_account`、`player_resource`

5. 进入对局：`match_room`、`match_player`
6. 结算：`match_result`、`reward_log`、`player_rank`

## 18. 结论

《动物园和声》MVP 服务端的数据核心，实际上只有三件事：

1. 管好玩家资产
2. 管好构筑合法性
3. 管好对局可复算性

只要这三件事站住，后面的抽卡、赛季、活动和技能扩展都能在这套表结构上自然生长。

## 19. 微信小游戏适配参考

以下内容仅作为后续适配微信小游戏时的参考，不影响 TapTap Android 首发的数据主结构：

1. `primary_platform` 可取值 `wechat_game`。
2. `platform_user_id` 在微信平台下可映射为 `openid`。
3. `platform_union_id` 在微信平台下可映射为 `unionid`。
4. 若需要记录微信专属字段，建议新建渠道扩展表，而不是污染主账号表。
